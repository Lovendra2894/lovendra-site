Selected work

Automated merchant payouts on Cashfree

Merchants were paid their settlement amounts by manual bank transfer every cycle. I replaced that with an automated payout system, carried from a written design spec through to production: ledger schema, signed-webhook handling, reconciliation for transfers that go quiet, and an admin surface.

The hard part of moving money is not moving it. It is guaranteeing you never move it twice. The ledger row is written before the provider is called, so a crash can never leave money transferred with no record of it. Two layers of idempotency sit on top — application logic, and a generated-column unique index as the database-level backstop for the check-then-insert race.

Transfer states — and which one is allowed to retry
PENDINGIn flight. Blocks a second attempt, because the provider may still be processing it.
SUCCESSAlready paid. Blocks permanently. Only a reversal may reopen it.
FAILEDThe one retryable state. Its unique key is NULL, so the index exempts it and a genuine retry stays possible.

Where the provider might have accepted a transfer despite returning an error, the row deliberately stays PENDING rather than being marked failed. A reconciliation sweep resolves it later. That is the uncomfortable choice — a row can sit unresolved, which looks worse operationally — but it cannot lose money.

Payments that recover themselves

A partner paid by UPI. The provider captured the money. The onboarding record sat unprocessed for four days and surfaced only because the partner complained. The system had exactly two ways to learn a payment had succeeded, both external: the app returning from the payment sheet, and the provider's webhook. When both missed, nothing ever revisited the record.

I added a third path, in two forms. The status endpoint now self-heals on the partner's next app open, and a bounded admin sweep recovers records for partners who never come back. The safety comes from reuse rather than relaxation: the recovery path runs the same capture verification and the same atomic status flip that the webhook and confirmation callbacks already race through, so a concurrent callback still cannot advance a purchase twice.

Angular 7 to 17, on a live merchant dashboard

The dashboard every merchant works in was pinned to Angular 7, released in 2018. An earlier attempt by someone else to reach Angular 15 never became mainline. I took it to 16, then to 17, as two staged upgrades across 956 files.

The proof it worked is not a commit. It is a branch: the upgrade branch is still the team's integration trunk two and a half years later, with 618 merge requests landed into it. Most migrations fail at exactly that point — the merge into mainline, and the maintenance after.

Ten days, twelve Angular majors

A support console stuck on Angular 4. I moved it version by version through 5, 6 and 7 — where the breaking changes are structural — then in a single jump to 14 and on to 16, finishing eleven days after I started. The final step removed far more code than it added, which is what a migration should look like when it is deleting shims rather than rewriting features.

I shipped ticketing features in the same window. The roadmap did not freeze behind the upgrade.

Making the database behave

A core legacy API was returning cyclic data and looping indefinitely. I rewrote it; active MySQL connections fell from over 1,200 to a steady 300–700, and p95 latency went from 76 ms to 48 ms at more than 17,000 transactions a day.

Separately: a critical query taken from 6.8 seconds to 5 milliseconds through targeted indexing, and a nine-month table-partitioning backlog cleared with Percona Toolkit at zero downtime.

How I work

I write a design spec and an implementation plan before the code, and I got the backend team doing the same. Eighteen of them last year, three over 980 lines, plus change notes handed to the mobile team ahead of every breaking release.

The habit earns its cost on exactly the work above.
